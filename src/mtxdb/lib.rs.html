1//! mtxdb: a write-once, content-addressed packfile storage engine for Matrix.
2//!
3//! Records are append-only versions, including explicit removal versions;
4//! physical reclamation happens during background repack, which rewrites only
5//! reachable data in traversal order.
6//!
7//! # Removal
8//!
9//! Removing a key (`DatabaseTransaction::remove` / `remove_many`) appends a new
10//! version of the record: an empty frame carrying `FLAG_REMOVED`. It is not a
11//! tombstone in the index or the redo/delta logs; the index entry simply points
12//! at the newest version, and every read, scan and count of live records treats
13//! a removed version as absent. An empty payload alone is an ordinary live
14//! value. Removing a key that is not live writes nothing and leaves the
15//! collection version unchanged, and a later put of the same key supersedes the
16//! removal.
17//!
18//! Space comes back only at repack. A repack drops a removal marker once no
19//! older copy of the key can survive, and carries it forward while a retained
20//! shard (one another collection still references) may still hold the older
21//! value, so a rebuild from the shards never brings the key back. The order of
22//! versions is the pack's creation sequence and the frame's offset, never the
23//! runtime shard slot or a journal LSN.
24//!
25//! # Compatibility
26//!
27//! Removal is a one-way format addition. A pack that holds a removal frame sets
28//! a frame flag that builds without removal support reject (an unknown frame
29//! flag is an error, never skipped), and a journal group that holds a removal
30//! uses a mutation kind those builds reject as malformed. Either way an older
31//! build refuses to open the store rather than ignore a removal or read the
32//! older value; it does not truncate the journal. A store that has never
33//! recorded a removal remains readable by older builds.

43// On disk the source is grouped by layer, with each module's tests beside it:
44//   engine/  the storage engine: packfiles, shards, journal, database, layout,
45//            the hash index, templates and record classes;
46//   graph/   ordered, adjacency and closure primitives built on the engine:
47//            short ids, closure generations, logical heads, bitmap sets, the
48//            timeline, auxiliary indexes and the graph helpers;
49//   matrix/  the Matrix-specific adapters: event adjacency, room-version
50//            policy, state groups, auth closures and the room auth facade.
51// The module tree stays flat: each module below names its file with `#[path]`,
52// so every `crate::journal::...` and `mtxdb::journal::...` path is unchanged.
